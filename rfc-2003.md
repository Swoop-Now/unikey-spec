## Abstract

Scope containment is a normative requirement throughout the UniKey suite: delegation chains MUST only narrow authority (RFC 2001 §9, RFC 1200 §2, RFC 1400 §3.2), and verifiers MUST reject any chain in which scope expands. Enforcing that requirement deterministically demands a precise definition of what a scope string is and how two scopes are compared. This document defines the scope grammar, the registry of reserved scope verbs, and the normative subset-comparison algorithm that all conforming implementations and verifier libraries MUST use. It supersedes the informal scope notations used in earlier drafts (`pay:max_100`, the separate `constraints` field of RFC 1200 v1.0).

---

## 1. Introduction

Prior to this document, scope strings appeared across the suite in three inconsistent shapes: bare verbs (`"pay"`), verb-with-limit (`"charge:100"`), and prefixed limits (`"pay:max_100"`), with numeric constraints sometimes expressed in a separate optional `constraints` field. A verifier cannot deterministically evaluate "is `charge:50` a subset of `charge:100`?" without a normative grammar and comparison rule. This document provides both, so that scope checking can be implemented identically in every verifier library.

## 2. Terminology

The key words MUST, MUST NOT, SHOULD, SHOULD NOT, and MAY in this document are to be interpreted as described in RFC 2119.

- **Scope string:** A single element of the `claims.scope` array of a Trust Packet.
- **Verb:** The first segment of a scope string, naming the class of action.
- **Qualifier:** An optional segment constraining the verb.
- **Parent / child:** Adjacent packets across a delegation boundary; the child's authority derives from the parent's.

## 3. Scope Grammar (Normative)

A scope string is composed of colon-separated segments:

```
scope-string = verb [ ":" qualifier ]
verb         = registered-verb / extension-verb
extension-verb = "x-" 1*( ALPHA / DIGIT / "_" / "-" )
qualifier    = numeric-limit / resource-token
numeric-limit  = 1*DIGIT [ "." 1*DIGIT ]
resource-token = 1*( ALPHA / DIGIT / "_" / "-" / "." / "*" )
```

Rules:

1. The verb MUST be either a value from the Scope Verb Registry (§5) or an extension verb carrying the `x-` prefix.
2. A **numeric qualifier** expresses an authorized ceiling in the currency or unit established by the action context (e.g., `charge:100` = authority to charge at most 100). Numeric qualifiers MUST be non-negative decimals.
3. A **resource qualifier** names a resource class or instance (e.g., `browse:products`). The wildcard `*` matches any resource and is equivalent to omitting the qualifier.
4. An **unqualified verb** (e.g., `pay`) grants unbounded authority for that verb. Issuers SHOULD always qualify verbs that support qualification.
5. The legacy `max_` prefix (`pay:max_100`) is deprecated. Implementations encountering it MUST treat `max_<n>` as equivalent to the numeric qualifier `<n>`.
6. The `constraints` field of RFC 1200 v1.0 is deprecated; numeric limits MUST be expressed as scope qualifiers.

## 4. Subset Comparison Algorithm (Normative)

A child scope array `C` is contained by a parent scope array `P` if and only if **every** scope string in `C` is covered by **at least one** scope string in `P`.

A child scope string `c` is covered by a parent scope string `p` when all of the following hold:

1. **Verb match:** `verb(c) == verb(p)`. Verbs never cover other verbs; there is no verb hierarchy.
2. **Qualifier narrowing:**
   - If `p` is unqualified (or its qualifier is `*`), any qualifier on `c` is permitted.
   - If `p` has a numeric qualifier, `c` MUST have a numeric qualifier and `value(c) <= value(p)`.
   - If `p` has a resource qualifier, `c` MUST have a resource qualifier equal to `p`'s (exact, case-sensitive string match).
   - If `p` is qualified and `c` is unqualified, `c` is NOT covered (an unqualified child would widen authority).
   - A numeric qualifier never covers a resource qualifier or vice versa; mixed comparison MUST fail.

```
function scopeArrayContained(child[], parent[]):
  for c in child:
    if not any(covers(p, c) for p in parent):
      return false
  return true

function covers(p, c):
  if verb(p) != verb(c): return false
  if qualifier(p) is absent or "*": return true
  if qualifier(c) is absent: return false
  if isNumeric(qualifier(p)) and isNumeric(qualifier(c)):
    return value(c) <= value(p)
  if isResource(qualifier(p)) and isResource(qualifier(c)):
    return qualifier(c) == qualifier(p)
  return false
```

Numeric comparison MUST be performed on decimal values, not on string representations. Comparison MUST fail closed: any scope string that cannot be parsed under the grammar in §3 MUST cause the containment check — and therefore the packet or certificate — to be rejected (TP-004).

A terminal action's scope (e.g., `charge:49.99` for an actual charge of 49.99) is compared against its delegated authority with the same algorithm: the action amount is a numeric qualifier and MUST satisfy `value(action) <= value(delegated ceiling)`.

## 5. Scope Verb Registry

Initial registered verbs:

| Verb | Meaning | Qualifier form |
|------|---------|----------------|
| `pay` | Transfer funds | numeric ceiling |
| `charge` | Charge a payment instrument | numeric ceiling |
| `refund` | Reverse a prior charge | numeric ceiling |
| `browse` | Read-only catalog or resource access | resource token |
| `read` | Read a resource | resource token |
| `write` | Create or modify a resource | resource token |
| `execute` | Invoke an API or service operation | resource token |
| `delegate` | Issue further delegation packets | resource token |
| `notify` | Send a notification or message | resource token |

Rules:

1. Unregistered verbs without the `x-` prefix MUST cause rejection (fail closed, consistent with RFC 2001 §5.7).
2. Extension verbs (`x-` prefix) are permitted for private deployments. Both parties to a delegation must recognize an extension verb; a verifier that does not recognize an extension verb MUST reject.
3. Registry additions require a version increment of this document.

## 6. Library Requirements

Conforming verifier libraries (Go, Rust, TypeScript reference implementations) MUST:

1. Expose scope parsing that enforces the grammar in §3, including `max_` legacy normalization.
2. Expose the containment check of §4 as the sole scope-comparison entry point — implementations MUST NOT substitute string-prefix or regex comparison.
3. Reject unparseable scopes, unknown verbs, and mixed qualifier comparisons (fail closed).
4. Evaluate containment at every delegation boundary of a chain (RFC 1200 §4, RFC 1400 §3.2), not only at the terminal action.

## 7. Security Considerations

- **Escalation via grammar ambiguity:** The single normative grammar eliminates comparisons in which two implementations disagree about whether a scope narrows.
- **Unqualified-scope widening:** Rule §4.2 (qualified parent never covers unqualified child) prevents a delegate from dropping a ceiling.
- **Unit confusion:** Numeric qualifiers carry no currency/unit; the unit is fixed by the action context of the chain. Chains MUST NOT mix units across a delegation boundary without an explicit resource qualifier distinguishing them.
- **Parser divergence:** Fail-closed parsing ensures a malformed scope cannot be interpreted permissively by one verifier and strictly by another.

## 8. Conformance

An implementation is conformant with UniKey RFC 2003 if it:

1. Parses scope strings exclusively under the §3 grammar.
2. Implements the §4 containment algorithm exactly, failing closed on any parse or comparison error.
3. Rejects unregistered, non-extension verbs.
4. Treats deprecated forms (`max_` prefix, RFC 1200 v1.0 `constraints`) per the normalization rules in §3.
