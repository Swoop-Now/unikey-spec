## Abstract

Trust Packets are transport-agnostic (RFC 2001 §10), and email is one of the transports the suite has always contemplated — but until this document, the suite specified only the sender-authentication posture for email (SPF, DKIM, DMARC; RFC 2001 §11) and key discovery (RFC 3002), not how a Trust Packet is actually carried in a message. This profile defines message construction, MIME placement, encoding, size constraints, inbound processing, and asynchronous result delivery for conveying Trust Packets and Authorization Certificates over SMTP. It is a use-case profile of the core Authorization Flow (RFC 5003 §12).

---

## 1. Scope

This document profiles email conveyance only. It does not alter the Trust Packet format, verification procedure, or trust model: security derives solely from the canonical packet and its signatures, never from transport metadata (RFC 2001 §10, RFC 5003 §9). Everything in this profile concerns reliable carriage and deterministic extraction.

## 2. Terminology

The key words MUST, MUST NOT, SHOULD, SHOULD NOT, and MAY are to be interpreted as described in RFC 2119.

- **Sending operator:** The domain operator transmitting Trust Packet email (RFC 2001 §11).
- **Receiving verifier:** The system that extracts and verifies Trust Packets from inbound mail.

## 3. Message Construction

### 3.1 MIME Placement

1. A Trust Packet MUST be carried as a MIME part with media type `application/unikey-trust-packet+json`.
2. An Authorization Certificate MUST be carried as a MIME part with media type `application/unikey-authorization-certificate+json`.
3. The packet part SHOULD be a direct child of the top-level `multipart/mixed` (or the sole body part). A human-readable `text/plain` or `text/html` part MAY accompany it; the human-readable part is informational and MUST NOT be used for verification.
4. A message MUST NOT carry more than one Trust Packet part. Multi-packet sequences are conveyed either as an Authorization Certificate part or as separate messages linked via `header.chain` (RFC 2001 §5.5).

### 3.2 Encoding

1. The part content MUST be the packet's JSON, UTF-8 encoded, without BOM (consistent with canonicalization; RFC 2001 §5.3).
2. Content-Transfer-Encoding MUST be `base64` or `quoted-printable`; `base64` is RECOMMENDED. Raw 8bit encoding MUST NOT be used — intermediate MTAs may re-wrap lines, and although canonicalization protects the hash, deterministic extraction is simpler under base64.
3. The packet MUST verify against its canonical form after decoding; any transformation applied by the mail system that survives decoding invalidates signatures and MUST result in rejection (fail closed).

### 3.3 Message Headers

1. The message SHOULD include an `X-UniKey-TPH` header carrying the Trust Packet Hash and an `X-UniKey-Packet-Id` header carrying the `packet_id`, for routing, deduplication, and log correlation.
2. These headers are transport metadata: verifiers MUST NOT treat them as authoritative and MUST NOT skip full verification because a header matches.
3. The full Trust Packet MUST NOT be placed in message headers. Header size limits in common MTA implementations (998-character line limit, typical 8–64 KB total header caps) cannot accommodate the 16 KB maximum packet size (RFC 2001 §7).
4. Packets conveyed under this profile SHOULD set `header.transport` to `smtp` (RFC 2001 §5.6).

## 4. Sender Authentication

The sending operator MUST satisfy RFC 2001 §11 in full: SPF authorizing only the operator's infrastructure, DKIM signing with an HSM-held key published per RFC 3002, and DMARC with a reject policy. SPF/DKIM/DMARC gate *message acceptance*; they are independent of, and in addition to, Trust Packet signature verification.

## 5. Inbound Processing (Normative)

Receiving verifiers MUST process inbound Trust Packet mail in this order:

1. Enforce SPF, DKIM, and DMARC per RFC 2001 §11. Failure → discard the message; the packet is never parsed.
2. Locate the single `application/unikey-trust-packet+json` (or certificate) part. Zero parts or multiple parts → reject.
3. Decode the part per its Content-Transfer-Encoding.
4. Verify the Trust Packet per RFC 2001 §6 (or the certificate per RFC 1400 §3), exactly as for any other transport.
5. Auto-replies, forwards, and mailing-list retransmissions fail DMARC alignment and are correctly rejected at step 1 (RFC 2001 §11.4).

Email delivery latency counts against the packet's `expires_at`. Sending operators SHOULD set expirations that accommodate expected delivery delay; verifiers MUST NOT extend temporal validity to compensate for slow delivery (fail closed).

## 6. Asynchronous Result Delivery

Email is a one-directional transport, matching the asynchronous flow of RFC 1400 §2.6:

1. If the inbound packet carries `header.callback_url`, the verification result SHOULD be delivered to that URL.
2. Otherwise, the result MAY be returned by email to the authenticated sending domain. A result message MUST itself carry a Trust Packet (`packet_type: "action_response"`) linked to the request via `header.chain.parent_packet_hash`, and MUST satisfy §3–§4 of this profile in the reverse direction.
3. Correlation MUST rely on the signed chain link, not on `In-Reply-To`/`References` headers, which are unauthenticated transport metadata.

## 7. Security Considerations

- **Transport metadata is not trust:** Nothing in this profile adds authority to a packet. A message that passes SPF/DKIM/DMARC but carries an invalid packet is rejected; a valid packet arriving over a misconfigured channel is also rejected (step 1 precedes parsing).
- **Replay across transports:** The nonce registry (RFC 2001 §4) is transport-independent; a packet observed over HTTPS and replayed over email MUST be rejected.
- **Size:** Certificates approach 64 KB (RFC 1400 §6); operators MUST ensure their mail infrastructure accepts such messages or convey the certificate by `cert_id` reference instead.

## 8. Conformance

An implementation is conformant with UniKey RFC 5004 if it:

1. Constructs messages per §3 (MIME placement, encoding, header rules).
2. Enforces the full RFC 2001 §11 sender-authentication posture before parsing any packet.
3. Processes inbound mail in the normative order of §5.
4. Correlates asynchronous results only through signed chain links (§6).
