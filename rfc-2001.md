## Abstract

The UniKey Trust Packet is a universal, transport-agnostic cryptographic container for proving identity, authority, and intent. It enables any verifier—without prior integration, shared state, or platform dependency—to deterministically decide whether an action is authorized. Trust Packets are designed to survive hostile or lossy internet transports, remain independently verifiable by any party, and fail closed under ambiguity or attack. This specification defines the invariant foundation for secure agent action, payments, and authentication across the open internet.

---

## 1. Introduction

A Trust Packet is a self-contained, cryptographically signed data structure that asserts identity, authority, and intent. Unlike session-based authentication, a Trust Packet carries its own proof of validity, allowing it to be transmitted across heterogeneous environments (email headers, APIs, QR codes, or message queues) while maintaining cryptographic integrity.

## 2. Scope

This document specifies the canonical packet structure, required fields, and the deterministic rules for canonicalization, hashing, and signature encoding. It further defines multi-signature support and delegation chain semantics. It does not define specific transport protocols or business-layer policy interpretation.

## 3. Terminology

The key words MUST, MUST NOT, SHOULD, SHOULD NOT, and MAY in this document are to be interpreted as described in RFC 2119.

- TPH (Trust Packet Hash): The unique cryptographic digest of a canonicalized packet.
- Verifier: Any entity that receives a Trust Packet and evaluates its signatures and claims.

## 4. Requirements (Normative)

1. Implementations MUST ensure packets remain verifiable across lossy transports.
2. Verification MUST fail closed; any partial validation or ambiguity MUST result in a rejected packet.
3. Canonicalization MUST be applied prior to hashing to ensure deterministic results across different platforms.
4. Every Trust Packet MUST include a mandatory audience field binding the packet to the intended relying party domain. Verifiers MUST reject Trust Packets where the audience field does not match their own domain.
5. Every Trust Packet MUST include a cryptographically random nonce of no fewer than 128 bits, incorporated into the canonical form prior to signing. Verifiers MUST maintain a nonce registry within the validity window and MUST reject any Trust Packet presenting a previously observed nonce or an expired timestamp.

## 5. Specification

### 5.1 Logical Structure

A Trust Packet is composed of four top-level components:

- Header: Protocol metadata.
- Claims: Identity, authority, and context assertions.
- Payload: Action-specific data (opaque to the protocol).
- Signatures: An array of one or more cryptographic attestations.

### 5.2 Required Fields

| Field | Component | Description |
|-------|-----------|-------------|
| tp_version | header | Format version (e.g., "1.0") |
| packet_type | header | Packet purpose (e.g., "action_request", "action_response") |
| packet_id | header | Globally unique identifier (UUID) |
| issued_at | header | UTC timestamp (ISO 8601) |
| expires_at | header | UTC expiration timestamp |
| nonce | header | Cryptographically random value (minimum 128 bits) |
| canonicalization | header | Canonicalization scheme identifier (e.g., "unikey-json-v1") |
| subject | claims | The identity being asserted |
| issuer | claims | The signing authority |
| audience | claims | Intended relying party domain |
| scope | claims | Array of allowed actions |
| context | claims | Free-form correlation context (MAY be empty) |
| delegation_chain | claims | Ordered array of delegating identities (MAY be empty) |
| action | payload | The action being requested or attested |
| params | payload | Action-specific parameters (opaque to the protocol) |
| message | payload | Optional human-readable message (null if absent) |
| signatures | (top-level) | Array of cryptographic signature objects |

Optional field:

| Field | Component | Description |
|-------|-----------|-------------|
| prev_packet_hash | payload.params | TPH of the immediately preceding packet in a chain (see §5.5) |

### 5.3 Canonicalization Rules (UniKey-JSON-v1)

To ensure identical hashes across different systems, the following rules MUST be applied:

1. Lexicographical Ordering: All fields MUST be ordered alphabetically by key name.
2. Encoding: MUST use UTF-8 without a Byte Order Mark (BOM).
3. Whitespace: MUST remove all insignificant whitespace and line breaks.
4. Binary Data: MUST be encoded using base64url without padding.

### 5.4 Hashing and Signing

1. Construct the packet excluding the signatures field.
2. Apply UniKey-JSON-v1 canonicalization to produce the canonical byte string.
3. Compute the digest of the canonical byte string using the specified hash function (default: SHA-256) to produce the TPH. The TPH uniquely identifies the packet and serves as the chain-link value (§5.5).
4. All signatures in the signatures array MUST be computed over the canonical byte string. Algorithms with internal hashing (e.g., Ed25519, the default) sign the canonical byte string directly; pre-hashed variants MUST sign the TPH and MUST declare a distinct algorithm identifier.

### 5.5 Packet Chaining

Multi-step flows (e.g., authorization → quote → approval) MAY link Trust Packets into a tamper-evident chain:

1. A packet is chained to its predecessor by embedding the predecessor's TPH as `prev_packet_hash` inside `payload.params`.
2. Because `payload` is part of the canonical form, the embedded hash is covered by the packet's signatures. Altering any byte of a predecessor changes its TPH and breaks every subsequent link.
3. Verifiers presented with a chained packet MUST recompute the predecessor's TPH from its canonical form and compare it to the embedded `prev_packet_hash`. A mismatch MUST result in rejection (TP-006).
4. Chain hashing is key-independent: link integrity is verifiable by any party that possesses the packets, regardless of which signature scheme attests them.

## 6. Verification Procedure (Normative)

```
function verifyTrustPacket(packet, prevPacket?):
  if packet.tp_version not supported:
    return TP-005 # Unsupported Version

  canonical = canonicalize(packet minus signatures)
  tph = hash(canonical)

  for sig in packet.signatures:
    pubkey = resolvePublicKey(sig.signer, sig.key_id)
    if not verifySignature(pubkey, canonical, sig.signature):
      return TP-002 # Signature Mismatch

  if now < packet.issued_at or now > packet.expires_at:
    return TP-003 # Temporal Failure

  if replayDetected(packet.nonce):
    return TP-001 # Replay/Canonicalization Error

  if packet.claims.audience != verifier.domain:
    return TP-007 # Audience Mismatch

  if not validDelegationChain(packet.claims.delegation_chain):
    return TP-004 # Delegation Chain Failure

  if packet.payload.params.prev_packet_hash exists:
    if hash(canonicalize(prevPacket minus signatures)) != packet.payload.params.prev_packet_hash:
      return TP-006 # Chain Integrity Failure

  return VALID
```

## 7. Operational Constraints

- Typical Size: < 4 KB
- Maximum Size: 16 KB (Packets exceeding this MAY be rejected).
- Latency Target: Verification SHOULD complete in < 5ms on commodity hardware.

## 8. Error Handling

| Code | Condition | Action |
|------|-----------|--------|
| TP-001 | Canonicalization/Replay Failure | Reject |
| TP-002 | Signature Validation Failure | Reject |
| TP-003 | Temporal Validity (Expired/Future) | Reject |
| TP-004 | Delegation Chain Failure | Reject |
| TP-005 | Unsupported Version/Algorithm | Reject |
| TP-006 | Chain Integrity Failure (prev_packet_hash mismatch) | Reject |
| TP-007 | Audience Mismatch | Reject |

## 9. Security Considerations

Trust Packets are designed for adversarial environments. Verifiers MUST assume transports are lossy and intermediaries are malicious.

- Integrity: Guaranteed by TPH signatures.
- Replay Resistance: Enforced via nonce and strict expires_at checks.
- Scope Containment: Delegation chains MUST only narrow authority; they can never expand it.

### 9A. Reference Threat Scenarios

- TS-1 (Replay): Attacker replays a valid packet. Mitigation: Nonce uniqueness and temporal checks.
- TS-2 (Escalation): A delegated packet attempts to add scopes. Mitigation: Verifiers enforce monotonic scope reduction.
- TS-3 (Mutation): Whitespace altered in transit. Mitigation: Canonicalization ensures the signature remains valid.
- TS-4 (Chain Tamper): An earlier packet in a multi-step flow is altered or substituted after the fact. Mitigation: Each subsequent packet embeds the predecessor's TPH inside its signed payload (§5.5); recomputation exposes the mismatch (TP-006).

## 10. Transport Considerations

Trust Packets are transport-agnostic. They MAY be conveyed via SMTP, HTTPS, Message Queues, or QR/NFC handoff. No transport-specific metadata is considered authoritative; security is derived solely from the packet itself.

## 11. Email Transport Security

### 11.1 Transport Agnosticism

UniKey is transport-agnostic. Trust Packets are cryptographically independent of their delivery mechanism. A Trust Packet delivered via email, HTTPS, QR code, or NFC carries identical cryptographic guarantees. The security of a Trust Packet is a function of the signing key and canonical hash — not the channel over which it travels.

### 11.2 SPF

The UniKey cloud service domain MUST publish an SPF record authorizing only UniKey cloud infrastructure as permitted senders. Mail originating from any server not listed in the SPF record MUST be rejected by the receiving verifier.

### 11.3 DKIM

The UniKey cloud service MUST sign all outbound Trust Packet email with DKIM using a private key held in a hardware security module. One authoritative public key per domain MUST be published in DNS. No relay party participates in the signing chain. Verification is a direct DNS lookup against the known UniKey domain.

### 11.4 DMARC

UniKey verification endpoints MUST enforce DMARC with a reject policy. Mail that fails SPF or DKIM alignment MUST be rejected. Auto-replies and forwarded messages fail DMARC alignment because they cannot produce a valid DKIM signature from the UniKey cloud service signing key. This is correct behavior — auto-replies are not valid Trust Packet delivery mechanisms.

## Appendix B: Conformance and Invariant Mapping

An implementation is conformant if and only if it:

1. Produces packets matching the lexicographical order defined in Section 5.
2. Rejects any packet failing temporal or signature validation.
3. Ensures that trust decisions occur below the application layer and above the transport layer.
