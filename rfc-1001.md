# UniKey RFC-1001: The Four Primitives

- **Title:** The Four Primitives
- **Status:** Draft
- **Category:** Standards Track
- **Version:** 1.0
- **Date:** March 2026
- **Authors:** Swoop Engineering Team
- **Canonical URL:** /rfc-1001

---

## Abstract

The UniKey protocol suite is built on exactly four cryptographic primitives. Together, they provide a complete authorization framework for the Machine Economy — from granting permission to recording proof of authorized actions. This document defines each primitive, its role in the architecture, and how the four compose into a unified trust model. Every UniKey interaction can be described in terms of these primitives.

---

## 1. Overview

Authorization in the physical world requires four things: an authority (who can grant permission), a credential (proof of that grant), a chain of custody (proving the credential traces back to the authority), and a record (proof the action was authorized). Digital systems have historically conflated or omitted one or more of these. UniKey separates them cleanly.

| # | Primitive | Role | Spec |
|---|-----------|------|------|
| 1 | **Authority Anchor** | Who grants permission | RFC 1300, RFC 3002 |
| 2 | **Trust Packet** | Unit of authority | RFC 2001 |
| 3 | **Authorization Certificate** | Chain of authority | RFC 1400 |
| 4 | **Authorization Ledger** | Proof of authorized actions | RFC 2002 |

---

## 2. Authority Anchor

An Authority Anchor is a cryptographic root of trust — the entity that can grant permission.

**Definition:** An Authority Anchor is the combination of:
- A **domain identity** (e.g., `user.example.com`)
- An **Ed25519 keypair** where the private key is held within a security boundary
- A **DNS TXT record** publishing the public key at `<selector>._domainkey.<domain>`

The Authority Anchor is "who." It answers the question: *who has the right to authorize this action?*

**Properties:**
- **Device-bound:** The private key MUST be protected by a hardware or OS security boundary (RFC 1300)
- **Discoverable:** The public key MUST be published via DNS for any verifier to find (RFC 3002)
- **Self-sovereign:** No central registry or certificate authority is required
- **Rotatable:** Multiple selectors allow key rotation without service interruption

**Example:** A user's smartphone holds an Ed25519 private key in Secure Enclave. The public key is published at `unikey._domainkey.user.example.com`. This smartphone is an Authority Anchor — it can sign Trust Packets that any service can verify.

**Relationship to other primitives:** An Authority Anchor signs Trust Packets. It is the root of every Authorization Certificate. Its actions are recorded in the Authorization Ledger.

---

## 3. Trust Packet

A Trust Packet is the atomic unit of authority — a single, self-contained, cryptographically signed authorization for a specific action.

**Definition:** A Trust Packet is a JSON container with four sections:
- **Header:** Protocol metadata (version, packet ID, timestamps, nonce)
- **Claims:** Identity and authority assertions (subject, issuer, audience, scope)
- **Payload:** Action-specific data (action name, parameters, message)
- **Signatures:** One or more Ed25519 signatures over the canonical hash

The Trust Packet is "what." It answers the question: *what action is being authorized, by whom, for whom, and within what limits?*

**Properties:**
- **Self-verifying:** Carries its own proof — no session state or middleware required
- **Transport-agnostic:** Works over HTTPS, email (SMTP+DKIM), WebSocket, QR, NFC, or any channel
- **Scope-bound:** Authority is limited to the declared scope (e.g., `charge:89.99`)
- **Audience-bound:** Valid only for the intended verifier
- **Temporally-bound:** Expires after a declared TTL
- **Replay-resistant:** Unique nonce and packet ID prevent reuse

**Full specification:** RFC 2001.

## 4. Authorization Certificate

An Authorization Certificate is a chain of Trust Packets that proves delegated authority from an Authority Anchor to a final action.

**Definition:** An Authorization Certificate is an ordered sequence of Trust Packets where:
- The **first packet** is signed by an Authority Anchor (the root)
- Each **subsequent packet** is a delegation that references its parent via hash link
- The **final packet** is the action being authorized
- Each link in the chain narrows or maintains the scope — it MUST NEVER expand it

The Authorization Certificate is "how." It answers the question: *how does this agent's authority trace back to the root?*

**Properties:**
- **Hash-linked:** Each packet references the canonical hash of its parent (RFC 1200 §4)
- **Monotonically scoped:** Scope can only narrow across delegation boundaries — never expand
- **Independently verifiable:** Any party can validate the entire chain without contacting a central server
- **Temporally constrained:** If any link expires or is revoked, the entire chain is invalid
- **Variable depth:** Supports direct authorization (depth 1) through multi-hop delegation (depth N)

**Example:** A user's device (Authority Anchor) delegates `["browse:products", "charge:100"]` to a payment service. The payment service delegates `["charge:50"]` to an AI agent. The AI agent signs a charge for $49.99. The Authorization Certificate contains all three Trust Packets — proving the $49.99 charge traces back to the user's device through a valid, scope-narrowing chain.

**Full specification:** RFC 1400.

---

## 5. Authorization Ledger

An Authorization Ledger is an append-only record of all authorized actions — the verifiable receipt book.

**Definition:** An Authorization Ledger is an ordered, immutable log where each entry contains:
- The **Trust Packet Hash (TPH)** of the verified packet
- The **verification result** (signer, subject, action, scope, timestamp)
- The **Authorization Certificate hash** (if delegation was involved)
- A **sequence number** and **hash of the previous entry** (ensuring ordering and tamper evidence)

The Authorization Ledger is "proof." It answers the question: *can we prove this action was authorized?*

**Properties:**
- **Append-only:** Entries MUST NOT be modified or deleted after creation
- **Hash-chained:** Each entry includes the hash of the previous entry, creating a tamper-evident chain
- **Queryable:** Supports lookup by packet ID, subject, signer, action, or time range
- **Replay prevention:** The ledger serves as the canonical nonce store — if a packet ID exists in the ledger, it has already been processed
- **Audit-ready:** Satisfies the reproducibility requirement of RFC 4001 §6

**Example:** After Stripe verifies a Trust Packet for a $49.99 Nike purchase, the verification result is appended to the ledger. Six months later, during a chargeback dispute, Stripe produces the ledger entry — cryptographic proof that the purchase was authorized by the user's device, delegated through a valid chain, and verified before execution.

**Full specification:** RFC 2002.

## 6. How the Four Primitives Compose

A complete UniKey authorization flow uses all four primitives:

```
1. AUTHORITY ANCHOR
   User's device holds Ed25519 key, published in DNS
        |
        | signs
        v
2. TRUST PACKET
   "Allow AI agent to charge up to $100 at Nike"
        |
        | delegates (scope narrows)
        v
   TRUST PACKET
   "Charge $49.99 for Nike Air Max"
        |
        | bundled into
        v
3. AUTHORIZATION CERTIFICATE
   [Device packet] → [Delegation packet] → [Action packet]
   Full chain, independently verifiable
        |
        | verified, then recorded in
        v
4. AUTHORIZATION LEDGER
   Entry #4821: TPH=sha256:abc123, subject=claude@user.example.com,
   action=charge, amount=$49.99, signer=user.example.com,
   verified_at=2026-03-24T10:30:00Z, prev_hash=sha256:def456
```

**The key insight:** Each primitive builds on the previous one. Authority Anchors sign Trust Packets. Trust Packets chain into Authorization Certificates. Authorization Certificates are verified and recorded in the Authorization Ledger. Remove any one primitive and the system is incomplete.

## 7. Security Model

The four primitives create a defense-in-depth security model:

| Attack | Blocked by |
|--------|-----------|
| Credential theft (stolen passwords, API keys) | Authority Anchor — requires device possession |
| Forged authorization | Trust Packet — Ed25519 signature over canonical hash |
| Scope escalation | Authorization Certificate — monotonic scope reduction |
| Replay attack | Authorization Ledger — packet ID uniqueness check |
| Disputed authorization | Authorization Ledger — tamper-evident proof of what was authorized |
| DNS poisoning | Authority Anchor — RFC 3001 multi-resolver consensus |

---

## 8. Conformance

An implementation claiming UniKey conformance MUST support all four primitives:

1. **Authority Anchor:** Generate device-bound keys and publish via DNS (RFC 1300, RFC 3002)
2. **Trust Packet:** Build, sign, canonicalize, and verify Trust Packets (RFC 2001)
3. **Authorization Certificate:** Validate delegation chains with hash linking and scope narrowing (RFC 1400)
4. **Authorization Ledger:** Maintain an append-only, hash-chained log of verified actions (RFC 2002)

Partial implementations MUST NOT claim UniKey conformance.
