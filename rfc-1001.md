- **Title:** The Four Primitives

- **Version:** 1.0
- **Date:** March 2026
- **Authors:** Swoop Engineering Team
- **Canonical URL:** /rfc-1001

## Abstract

The UniKey protocol is a distributed, pre-execution authorization system for digital actions. It introduces a new infrastructure layer between device initiation and system execution — operating upstream of settlement rails, payment systems, API execution, and autonomous agent frameworks. The protocol applies equally to digital actions initiated by human users and by autonomous AI agents.

The system is built on exactly four cryptographic primitives. Together, they form a complete, layered authorization stack for the Machine Economy — from establishing authority to recording proof of authorized actions. A fifth invention — the Authorization Flow Architecture (RFC 5003) — defines the pre-execution authorization sequence through which the four primitives compose into an integrated system. This document defines each primitive, its role in the architecture, and how all five inventions combine into a unified trust model.

---

## 1. Overview

Authorization in the physical world requires four things: an authority (who can grant permission), a credential (proof of that grant), a chain of custody (proving the credential traces back to the authority), and a record (proof the action was authorized). Digital systems have historically conflated or omitted one or more of these. UniKey separates them cleanly.

| # | Primitive | Role | Spec |
|---|-----------|------|------|
| 1 | **Authority Anchor** | Establish who or what holds cryptographic authority | RFC 1300, RFC 3002 |
| 2 | **Trust Packet** | Prove that a specific action was explicitly authorized before execution | RFC 2001 |
| 3 | **Authorization Certificate** | Chain Trust Packets from multiple parties into a complete, tamper-evident transaction record | RFC 1400 |
| 4 | **Authorization Ledger** | Store Authorization Certificates in distributed, independently verifiable, append-only records | RFC 2002 |

Each primitive is independently novel. The combination of all four as an integrated pre-execution authorization system represents a further independent invention. The Authorization Flow Architecture (RFC 5003) defines the deterministic, multi-party sequence through which these primitives operate together.

| # | System Component | Role | Spec |
|---|------------------|------|------|
| 5 | **Authorization Flow** | Pre-execution authorization sequence separating authority verification from action execution | RFC 5003 |

## 2. Authority Anchor

An Authority Anchor is a novel identity and authority model in which any person, device, or enterprise system establishes cryptographic authority over digital actions through domain-based public keys distributed via the Domain Name System (DNS), without requiring a centralized certificate authority, without requiring new hardware, and with the ability to serve as the root of authority for both human-initiated and agent-initiated digital transactions.

**Definition:** An Authority Anchor is the combination of:
- A **domain identity** (e.g., `user.example.com`)
- An **Ed25519 keypair** where the private key is held within a security boundary
- A **DNS TXT record** publishing the public key at `<selector>._domainkey.<domain>`

The Authority Anchor is "who." It answers the question: *who has the right to authorize this action?*

### 2.1 Three Classes of Authority Anchor

The Authority Anchor model supports three distinct classes:

**Human Authority Anchors:** A human user whose explicit approval constitutes the authorization for an action. The human's device generates and signs the Trust Packet upon the human's approval event (biometric confirmation, passcode entry, explicit system prompt approval). The human is the subject in the Trust Packet; their device is the issuer; their domain or their payment network's domain is the signer. The human clicking approve is the Authority Anchor event.

**Device Authority Anchors:** A physical device — smartphone, tablet, laptop, IoT device, vehicle — that is bound to a domain-based authority. When a device manufacturer (e.g., Samsung) operates an authority domain, every device they manufacture can be an Authority Anchor bound to that manufacturer's domain. When a payment network (e.g., Visa) provisions a key into a device's Secure Enclave at card enrollment, that payment network's domain becomes the Authority Anchor for payment transactions from that device.

**Enterprise System Authority Anchors:** An organization's automated systems, AI agents, or enterprise platforms that hold authority through the organization's corporate domain. An enterprise deploying AI agents can anchor every agent action through the corporate domain's published keys, establishing verifiable organizational authority over all automated actions.

### 2.2 Properties

- **Device-bound:** The private key MUST be protected by a hardware or OS security boundary (RFC 1300)
- **Discoverable:** The public key MUST be published via DNS for any verifier to find (RFC 3002)
- **Self-sovereign:** No central registry or certificate authority is required — keys are self-published by the domain owner via DNS
- **Rotatable:** Multiple selectors allow key rotation without service interruption
- **Embeddable:** The Authority Anchor identity, domain, and key selector are embedded within every Trust Packet produced, enabling single-step verification without external infrastructure contact at verification time
- **Universal:** The same authority model applies uniformly to human actors, physical devices, and autonomous software systems

**Example:** A user's smartphone holds an Ed25519 private key in Secure Enclave. The public key is published at `unikey._domainkey.user.example.com`. This smartphone is an Authority Anchor — it can sign Trust Packets that any service can verify.

**Relationship to other primitives:** An Authority Anchor signs Trust Packets. It is the root of every Authorization Certificate. Its actions are recorded in the Authorization Ledger.

## 3. Trust Packet

A Trust Packet is a self-contained, transport-agnostic, cryptographically signed authorization container that proves identity, authority, and intent in a single verifiable object, enabling any conforming verifier to deterministically validate the authorization of a digital action before execution without shared state, prior bilateral integration, or contact with centralized infrastructure.

**Definition:** A Trust Packet is a JSON container with four sections:
- **Header:** Protocol metadata (version, packet ID, timestamps, nonce)
- **Claims:** Identity and authority assertions (subject, issuer, audience, scope)
- **Payload:** Action-specific data (action name, parameters, message)
- **Signatures:** One or more Ed25519 signatures over the canonical hash

The Trust Packet is "what." It answers the question: *what action is being authorized, by whom, for whom, and within what limits?*

**Properties:**
- **Self-verifying:** Carries its own proof — no session state or middleware required
- **Transport-agnostic:** Works over HTTPS, email (SMTP+DKIM), WebSocket, QR, NFC, or any channel
- **Scope-bound:** Authority is limited to the declared scope (e.g., `charge:89.99`)
- **Audience-bound:** Valid only for the intended verifier
- **Temporally-bound:** Expires after a declared TTL
- **Replay-resistant:** Unique nonce and packet ID prevent reuse
- **Pre-execution:** Authority is verified BEFORE the action is executed — not after submission

**Full specification:** RFC 2001.

## 4. Authorization Certificate

An Authorization Certificate is a cryptographically chained, multi-party transaction record that links together a sequence of Trust Packets — each signed by a different Authority Anchor under a different domain-based key — into a single tamper-evident, independently verifiable, uniquely identified record of a complete authorized transaction, with all signing parties' public keys embedded for self-contained verification.

**Definition:** An Authorization Certificate is an ordered sequence of Trust Packets where:
- The **first packet** (TP1) is signed by the originating Authority Anchor
- Each **subsequent packet** incorporates a cumulative hash of all preceding packets (TP2 incorporates hash of TP1; TP3 incorporates hash of TP1+TP2)
- Each packet in the chain is signed by a **different Authority Anchor** using a different domain-based key (multi-party, multi-anchor architecture)
- The certificate is formed at **transaction completion** — the natural completion of a payment, service delivery, or API call
- All signing parties' **public keys are embedded** directly within the certificate, enabling self-contained verification without DNS lookup
- Each link in the chain narrows or maintains the scope — it MUST NEVER expand it

The Authorization Certificate is "how." It answers the question: *how does this agent's authority trace back to the root?*

**Properties:**
- **Cumulative hash chain:** Each packet commits to the entire sequence of authorized actions preceding it — TP2 incorporates hash of TP1, TP3 incorporates hash of TP1+TP2. The final Trust Packet contains a hash that is a deterministic function of every preceding packet.
- **Multi-party, multi-anchor:** Each packet is signed by a different Authority Anchor, distinct from multi-signature schemes where multiple parties sign the same object
- **Monotonically scoped:** Scope can only narrow across delegation boundaries — never expand
- **Self-contained verification:** All public keys needed for verification are embedded within the certificate itself — no DNS lookup or external infrastructure contact required at verification time
- **Tamper-evident by construction:** Any modification, insertion, deletion, or reordering of any packet invalidates the hash relationships and makes tampering mathematically detectable
- **Formed at transaction completion:** The certificate is assembled when a transaction naturally completes, reformatted into a structured, human-readable and machine-readable representation with a unique searchable identifier
- **Variable depth:** Supports direct authorization (depth 1) through multi-hop delegation (depth N)

**Example:** A user's device (Authority Anchor) delegates `["browse:products", "charge:100"]` to a payment service. The payment service delegates `["charge:50"]` to an AI agent. The AI agent signs a charge for $49.99. The Authorization Certificate contains all three Trust Packets — proving the $49.99 charge traces back to the user's device through a valid, scope-narrowing chain — with all three parties' public keys embedded for independent verification.

**Full specification:** RFC 1400.

## 5. Authorization Ledger

An Authorization Ledger is a distributed, append-only, cryptographically verifiable record system in which each party to a transaction independently maintains an identical complete copy of the transaction's Authorization Certificate, where each copy is independently verifiable by any party using only the public keys embedded within the Certificate, without contact with any central authority, shared infrastructure, or consensus mechanism, and which may be operated by infrastructure-layer entities on behalf of entire participant ecosystems.

**Definition:** An Authorization Ledger is an ordered, immutable log where each entry contains:
- The **Authorization Certificate** (or its hash) for the completed transaction
- The **verification result** (signer, subject, action, scope, timestamp)
- A **sequence number** and **hash of the previous entry** (ensuring ordering and tamper evidence)

The Authorization Ledger is "proof." It answers the question: *can we prove this action was authorized?*

**Properties:**
- **Distributed:** Each party independently maintains their own identical copy — no shared ledger, no consensus mechanism required
- **Consistency through mathematics:** Consistency is guaranteed by the mathematical properties of the Authorization Certificate hash chain, not by synchronization or consensus protocols
- **Append-only by protocol:** Immutability is enforced at the protocol specification level, not dependent on access controls or administrative policy
- **Independently verifiable:** Any party can verify a ledger entry using only the public keys embedded within the Authorization Certificate — no DNS lookup, no external infrastructure contact required
- **Infrastructure-layer operation:** A telecom carrier, PSP, or payment network can operate ledgers on behalf of entire participant ecosystems, maintaining transaction records for all merchants or enterprises on their network
- **Hash-chained:** Each entry includes the hash of the previous entry, creating a tamper-evident chain
- **Queryable:** Supports lookup by packet ID, subject, signer, action, or time range
- **Replay prevention:** The ledger serves as the canonical nonce store — if a packet ID exists in the ledger, it has already been processed
- **Audit-ready:** Satisfies the reproducibility requirement of RFC 4001 S6

**Example:** After Stripe verifies a Trust Packet for a $49.99 Nike purchase, the verification result is appended to the ledger. Six months later, during a chargeback dispute, Stripe produces the ledger entry — cryptographic proof that the purchase was authorized by the user's device, delegated through a valid chain, and verified before execution. The embedded public keys in the Authorization Certificate allow any third party to independently re-verify the entry without contacting any external system.

**Full specification:** RFC 2002.

## 6. How the Five Inventions Compose

A complete UniKey authorization uses all four primitives, orchestrated through the Authorization Flow Architecture (RFC 5003). The flow enforces a critical architectural property: **authority is verified BEFORE execution** at every stage. This pre-execution model is normative and enforced at the protocol level.

```
1. AUTHORITY ANCHOR
   User's device holds Ed25519 key, published in DNS
   (Human, Device, or Enterprise System class)
        |
        | signs (pre-execution authorization)
        v
2. TRUST PACKET
   "Allow AI agent to charge up to $100 at Nike"
   Authority verified BEFORE action proceeds
        |
        | delegates (scope narrows, each party signs their own packet)
        v
   TRUST PACKET
   "Charge $49.99 for Nike Air Max"
   Cumulative hash links all preceding packets
        |
        | formed at transaction completion into
        v
3. AUTHORIZATION CERTIFICATE
   [Device packet] -> [PSP packet] -> [Agent packet]
   Multi-party, multi-anchor chain with embedded public keys
   Self-contained verification — no DNS lookup needed
        |
        | distributed to all parties, recorded in
        v
4. AUTHORIZATION LEDGER
   Each party independently maintains identical copy
   Verified using only embedded keys from the certificate
   Entry #4821: cert_id=cert_abc123, subject=claude@user.example.com,
   action=charge, amount=$49.99, verified_at=2026-03-24T10:30:00Z

   Orchestrated by:

5. AUTHORIZATION FLOW (RFC 5003)
   Seven-step pre-execution sequence:
   Action Initiation -> Request Forwarding -> Authorization Request ->
   Device Authorization -> Trust Packet Propagation -> Verification -> Execution
   Authority verified at every stage BEFORE execution proceeds
```

**The key insight:** Each primitive builds on the previous one. Authority Anchors sign Trust Packets. Trust Packets chain into Authorization Certificates. Authorization Certificates are distributed and recorded in Authorization Ledgers. The Authorization Flow Architecture defines the pre-execution sequence through which this composition occurs. Remove any one component and the system is incomplete.

## 7. Security Model

The four primitives and the Authorization Flow create a defense-in-depth security model rooted in pre-execution authorization:

| Attack | Blocked by |
|--------|-----------|
| Credential theft (stolen passwords, API keys) | Authority Anchor — requires device possession, not credential knowledge |
| Forged authorization | Trust Packet — Ed25519 signature over canonical hash |
| Scope escalation | Authorization Certificate — monotonic scope reduction across multi-anchor chain |
| Replay attack | Authorization Ledger — packet ID uniqueness check |
| Disputed authorization | Authorization Ledger — tamper-evident proof of what was authorized, independently verifiable via embedded keys |
| DNS poisoning | Authority Anchor — RFC 3001 multi-resolver consensus |
| Post-hoc authorization | Authorization Flow — pre-execution verification enforced at the protocol level; authority MUST be verified before execution proceeds |
| Chain manipulation | Authorization Certificate — cumulative hash chain makes insertion, deletion, or reordering mathematically detectable |

## 8. Conformance

An implementation claiming UniKey conformance MUST support all four primitives and operate within the Authorization Flow Architecture:

1. **Authority Anchor:** Generate device-bound keys and publish via DNS; support Human, Device, and Enterprise System anchor classes (RFC 1300, RFC 3002)
2. **Trust Packet:** Build, sign, canonicalize, and verify Trust Packets with pre-execution semantics (RFC 2001)
3. **Authorization Certificate:** Validate multi-party, multi-anchor delegation chains with cumulative hash linking, scope narrowing, and embedded public keys for self-contained verification (RFC 1400)
4. **Authorization Ledger:** Maintain a distributed, append-only, hash-chained log of verified actions, independently verifiable using only embedded keys from the Authorization Certificate (RFC 2002)
5. **Authorization Flow:** Implement the pre-execution authorization sequence separating authority verification from action execution (RFC 5003)

Partial implementations MUST NOT claim UniKey conformance.
