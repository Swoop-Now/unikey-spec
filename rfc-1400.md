## Abstract

An Authorization Certificate is a cryptographically chained, multi-party transaction record that links together a sequence of Trust Packets — each signed by a different Authority Anchor under a different domain-based key — into a single tamper-evident, independently verifiable, uniquely identified record of a complete authorized transaction, with all signing parties' public keys embedded for self-contained verification. Unlike individual Trust Packets (which prove a single authorization) or delegation chains (which are an abstract concept), an Authorization Certificate is a concrete, transportable artifact that bundles the complete proof of delegated authority. This specification defines the structure, validation rules, and transport encoding for Authorization Certificates.

---

## 1. Introduction

In simple authorization flows, a single Trust Packet signed by an Authority Anchor is sufficient. But in multi-party transactions — where a device authorizes a service, which authorizes an agent, which performs an action — the verifier needs to see the entire chain to confirm that authority was properly delegated at each step, with each party signing under their own Authority Anchor.

An Authorization Certificate packages this chain into a single artifact that can be transmitted, stored, and verified independently. The certificate is formed at transaction completion and embeds all signing parties' public keys, enabling any recipient to verify every signature in the chain without DNS lookup or external infrastructure contact.

## 2. Structure

An Authorization Certificate is a JSON object containing:

```json
{
  "cert_version": "1.0",
  "cert_id": "cert_<hex>",
  "created_at": "<ISO 8601 timestamp>",
  "chain": [
    { "<Trust Packet 1 — signed by first party's Authority Anchor>" },
    { "<Trust Packet 2 — signed by second party's Authority Anchor>" },
    { "<Trust Packet N — signed by Nth party's Authority Anchor>" }
  ],
  "chain_hashes": [
    "<TPH of packet 1>",
    "<cumulative hash: H(TP1)>",
    "<cumulative hash: H(TP1 + TP2)>",
    "<cumulative hash: H(TP1 + TP2 + ... + TP(N-1))>"
  ],
  "public_keys": [
    {
      "domain": "<Authority Anchor domain for TP1 signer>",
      "selector": "unikey",
      "public_key": "<base64 Ed25519 public key>",
      "packet_index": 0
    },
    {
      "domain": "<Authority Anchor domain for TP2 signer>",
      "selector": "unikey",
      "public_key": "<base64 Ed25519 public key>",
      "packet_index": 1
    },
    {
      "domain": "<Authority Anchor domain for TPN signer>",
      "selector": "unikey",
      "public_key": "<base64 Ed25519 public key>",
      "packet_index": "N-1"
    }
  ],
  "root_anchor": {
    "domain": "<Authority Anchor domain>",
    "selector": "unikey",
    "public_key": "<base64 Ed25519 public key>"
  },
  "terminal_action": {
    "subject": "<who is performing the final action>",
    "action": "<action name>",
    "audience": "<intended verifier>",
    "scope": ["<final narrowed scope>"]
  }
}
```

### 2.1 Required Fields

| Field | Description |
|-------|-------------|
| `cert_version` | Certificate format version (currently "1.0") |
| `cert_id` | Globally unique certificate identifier, assigned at transaction completion |
| `created_at` | ISO 8601 timestamp of certificate formation (at transaction completion) |
| `chain` | Ordered array of complete Trust Packets (first party's packet first, final action last) |
| `chain_hashes` | Ordered array of cumulative hashes — each entry is a hash incorporating all preceding packets |
| `public_keys` | Array of all signing parties' public keys, one per Trust Packet in the chain (see S2.3) |
| `root_anchor` | The Authority Anchor that is the root of this chain |
| `terminal_action` | Summary of the final action for quick inspection |

### 2.2 Chain Ordering

- `chain[0]` MUST be signed by the Authority Anchor identified in `root_anchor`
- `chain[N]` (the last packet) MUST be the action being authorized
- Each packet in the chain MUST be signed by a **different** Authority Anchor using a different domain-based key (multi-party, multi-anchor architecture)
- Intermediate packets MUST be delegation packets (packet_type: "delegation")
- A chain of length 1 is valid — it represents direct authorization without delegation

### 2.3 Embedded Public Keys

The `public_keys` array MUST contain the public key for every signing Authority Anchor in the chain. This is a critical distinguishing feature: in the base Trust Packet protocol, public keys are resolved via DNS at verification time. The Authorization Certificate captures and embeds these keys at formation, creating a self-contained verification package.

Each entry in `public_keys` MUST contain:

| Field | Description |
|-------|-------------|
| `domain` | The Authority Anchor domain that signed the corresponding packet |
| `selector` | The DKIM selector used to publish this key |
| `public_key` | The base64-encoded Ed25519 public key |
| `packet_index` | The index into `chain` identifying which packet this key signed |

A recipient can verify every signature in the chain using only the certificate itself — no DNS lookup or external infrastructure contact required.

### 2.4 Cumulative Hash Chain Mechanism

The hash chain within an Authorization Certificate uses cumulative hashing, not simple parent-child linking:

1. **Trust Packet 1 (TP1)** is generated and signed by the first party's Authority Anchor. Its hash is computed as TPH1 = SHA-256(canonical(TP1)).
2. **Trust Packet 2 (TP2)** incorporates a cryptographic hash of TP1 within its data structure before being signed by the second party's Authority Anchor.
3. **Trust Packet 3 (TP3)** incorporates a hash of the combination of TP1 and TP2 before being signed by the third party's Authority Anchor.
4. This pattern continues for each step in the transaction.

The result: each Trust Packet commits to the entire sequence of authorized actions preceding it. The final Trust Packet contains a hash that is a deterministic function of every preceding packet. Any modification, insertion, deletion, or reordering of any packet in the chain invalidates the hash relationships and makes the tampering mathematically detectable.

The chain is tamper-evident by construction, not by access control.

## 3. Validation Rules

Verifiers MUST apply the following rules to an Authorization Certificate:

### 3.1 Chain Integrity (Cumulative Hash Verification)

1. For Trust Packet 1, compute TPH1 and verify it matches `chain_hashes[0]`
2. For Trust Packet 2, verify that it incorporates TPH1, and compute the cumulative hash
3. For Trust Packet N, verify that it incorporates the cumulative hash of all preceding packets (TP1 through TP(N-1))
4. Verify that no packet can be inserted, removed, or reordered without breaking the cumulative hash chain

### 3.2 Scope Monotonicity

For each adjacent pair `(chain[i], chain[i+1])`:
- The scope of `chain[i+1]` MUST be a subset of or equal to the scope of `chain[i]`
- Scope MUST NEVER expand across a delegation boundary

### 3.3 Temporal Validity

1. Every packet in the chain MUST NOT be expired at the time of verification
2. Each delegation's expiration MUST be less than or equal to its parent's expiration
3. If any packet in the chain is expired, the entire certificate is INVALID

### 3.4 Signature Verification

Each packet in the chain MUST pass independent Ed25519 signature verification. Verification MAY use either source:

- **Self-contained (preferred for ledger verification):** Verify each packet's signature against the corresponding public key in the certificate's `public_keys` array
- **DNS-verified (preferred for real-time verification):** Verify each packet's signature against the signing entity's DNS-published public key

When verifying from a ledger entry or offline context, the embedded public keys enable complete verification without any external lookup.

### 3.5 Multi-Party, Multi-Anchor Verification

Each packet in the chain MUST be signed by a different Authority Anchor. This is distinct from multi-signature schemes where multiple parties sign the same object. Each party signs their own packet; the cumulative hash chain links independently-signed packets into a single sequential record.

The verifier MUST confirm that:
- Each packet is signed by the Authority Anchor domain identified in that packet's `signer` field
- The signing Authority Anchor for `chain[i+1]` corresponds to the delegated `subject` in `chain[i]`

### 3.6 Fail-Closed

If any validation step fails, the entire Authorization Certificate MUST be rejected. There is no partial validity.

## 4. Certificate Formation

An Authorization Certificate is formed at **transaction completion** — defined as the event at which a payment has been made, a service or product has been provided, or an API call has been completed and acknowledged.

Formation process:
1. Collect the complete Trust Packet sequence from the transaction
2. Reformat the data into the structured, human-readable and machine-readable certificate representation
3. Embed all public keys used by all signing parties directly within the certificate
4. Compute the cumulative hash chain across all packets
5. Assign a unique `cert_id`, making the complete record searchable and retrievable

The certificate assembler does NOT add a signature to the certificate itself — the individual Trust Packet signatures are the proof. The certificate is a packaging and archival format that captures the complete multi-party authorization record at the moment the transaction completes.

---

## 5. Privacy Accommodations

Default behavior provides complete, identical copies of the Authorization Certificate to all transaction parties.

Where privacy or regulation requires selective disclosure, the certificate format accommodates partial sharing while preserving hash chain integrity:

- Parties MAY share only metadata (identifiers, timestamps, verification status) while withholding content from specific Trust Packets
- The cumulative hash chain remains verifiable even when individual packet contents are redacted, because the hashes serve as commitments to the original content
- The unique `cert_id` enables reference and retrieval in contexts where full disclosure is permitted
- Selective disclosure MUST NOT compromise the ability to verify the hash chain structure

This privacy-accommodating variant preserves the mathematical tamper-evidence properties while permitting controlled disclosure of transaction data fields.

---

## 6. Transport

Authorization Certificates are transport-agnostic, like Trust Packets. They MAY be transmitted as:
- JSON body in an HTTPS POST
- Attachment or header in an email
- Embedded in a QR code (for short chains)
- Stored in a message queue
- Referenced by `cert_id` from an Authorization Ledger
- Distributed to all transaction parties at transaction completion

Maximum recommended size: 64 KB (supports chains up to ~4 levels deep with typical packet sizes).

## 7. Relationship to Trust Packets

A Trust Packet is a single authorization. An Authorization Certificate is a multi-party chain of Trust Packets.

| Aspect | Trust Packet | Authorization Certificate |
|--------|-------------|--------------------------|
| Scope | Single action | Multi-party transaction record |
| Depth | 1 signature | N signatures (each from a different Authority Anchor) |
| Hash chain | None | Cumulative — each packet commits to all preceding packets |
| Public keys | Resolved via DNS at verification | Embedded within the certificate |
| Self-contained | Yes | Yes (including all verification keys) |
| Independently verifiable | Yes (via DNS) | Yes (via embedded keys, no DNS needed) |
| Formation | At signing | At transaction completion |
| Use case | Direct authorization | Complete multi-party transaction proof |

An Authorization Certificate with a chain of length 1 is semantically equivalent to a standalone Trust Packet.

## 8. Example: AI Agent Purchase

```
Authority Anchors:
  - User device: user-device.example.com (Human Authority Anchor)
  - PSP: paymentservice.com (Enterprise System Authority Anchor)
  - AI Agent: agent.example.com (Enterprise System Authority Anchor)

chain[0] — TP1: Root Authorization (signed by user's device):
  subject: "psp@paymentservice.com"
  scope: ["charge:100"]
  packet_type: "delegation"
  signer: "user-device.example.com"
  -> "I authorize this PSP to charge up to $100"

chain[1] — TP2: PSP Delegation (signed by PSP):
  subject: "claude@agent.example.com"
  scope: ["charge:50"]
  cumulative_hash: H(TP1)
  packet_type: "delegation"
  signer: "paymentservice.com"
  -> "I delegate to this AI agent to charge up to $50"

chain[2] — TP3: Agent Action (signed by AI agent):
  subject: "claude@agent.example.com"
  action: "charge"
  scope: ["charge:49.99"]
  cumulative_hash: H(TP1 + TP2)
  signer: "agent.example.com"
  params: { item: "Nike Air Max", amount: 49.99 }
  -> "Charge $49.99 for Nike Air Max"

public_keys: [
  { domain: "user-device.example.com", public_key: "<key1>" },
  { domain: "paymentservice.com", public_key: "<key2>" },
  { domain: "agent.example.com", public_key: "<key3>" }
]
```

Verifier checks: $49.99 <= $50 <= $100. All signatures valid against embedded public keys. Cumulative hash chain intact: TP2 commits to TP1, TP3 commits to TP1+TP2. All packets unexpired. Each packet signed by a different Authority Anchor. **Certificate valid.**

## 9. Prior Art Differentiation

### 9.1 Blockchain

Blockchain chains blocks through hash linkage but: (a) requires consensus among network participants; (b) chains transactions within a global ledger rather than actions within a single transaction; (c) each block is created by a single miner rather than by multiple distinct parties each signing their own step; (d) is not formed at transaction completion as a self-contained multi-party record with embedded keys.

### 9.2 Multi-Signature Schemes

Multi-signature schemes require multiple parties to sign the same object. The Authorization Certificate has each party sign their own distinct Trust Packet which is then linked through the cumulative hash chain. Each signer operates under their own Authority Anchor with their own domain-based key.

### 9.3 Audit Logs

Audit logs record events after occurrence and are protected by access controls rather than cryptographic construction. Authorization Certificates record pre-execution authorizations and are tamper-evident by hash chain mathematics independent of access controls.

## 10. Security Considerations

- **Chain manipulation:** Cumulative hash linking prevents insertion, removal, or reordering of packets — any modification is mathematically detectable
- **Scope escalation:** Monotonicity check prevents a delegate from exceeding granted authority
- **Expired root:** Temporal validation ensures a revoked Authority Anchor invalidates all downstream certificates
- **Stale certificates:** Certificates SHOULD be assembled fresh at transaction completion, not cached
- **Key compromise after formation:** Embedded public keys reflect the state at transaction completion; certificates remain verifiable even if a key is later rotated
- **Multi-party accountability:** Each packet is independently signed by a different Authority Anchor, ensuring no single party can forge the complete chain

---

## 11. Conformance

An implementation is conformant with RFC 1400 if it:

1. Correctly assembles Authorization Certificates from ordered Trust Packet chains at transaction completion
2. Embeds all signing parties' public keys within the certificate's `public_keys` array
3. Validates the cumulative hash chain — each packet commits to all preceding packets
4. Enforces scope monotonicity across all delegation boundaries
5. Verifies that each packet is signed by a different Authority Anchor (multi-party, multi-anchor)
6. Rejects the entire certificate if any single packet fails validation
7. Supports self-contained verification using only the embedded public keys (no DNS lookup required)
8. Supports privacy accommodations for selective disclosure while preserving hash chain integrity
