## Abstract

An Authorization Certificate is a self-contained, verifiable chain of Trust Packets that proves an action's authority traces back to a cryptographic root. Unlike individual Trust Packets (which prove a single authorization) or delegation chains (which are an abstract concept), an Authorization Certificate is a concrete, transportable artifact that bundles the complete proof of delegated authority. This specification defines the structure, validation rules, and transport encoding for Authorization Certificates.

---

## 1. Introduction

In simple authorization flows, a single Trust Packet signed by an Authority Anchor is sufficient. But in delegated flows — where a device authorizes a service, which authorizes an agent, which performs an action — the verifier needs to see the entire chain to confirm that authority was properly delegated at each step.

An Authorization Certificate packages this chain into a single artifact that can be transmitted, stored, and verified independently.

---

## 2. Structure

An Authorization Certificate is a JSON object containing:

```json
{
  "cert_version": "1.0",
  "cert_id": "cert_<hex>",
  "created_at": "<ISO 8601 timestamp>",
  "chain": [
    { <Trust Packet 0 — root, signed by Authority Anchor> },
    { <Trust Packet 1 — delegation from root to delegate> },
    { <Trust Packet N — final action> }
  ],
  "chain_hashes": [
    "<TPH of packet 0>",
    "<TPH of packet 1>",
    "<TPH of packet N>"
  ],
  "root_anchor": {
    "domain": "<Authority Anchor domain>",
    "selector": "unikey",
    "public_key": "<base64 Ed25519 public key>"
  },
  "terminal_action": {
    "subject": "<who is performing the final action>",
    "action": "<action name>",
    "audience": "<intended verifier>",
    "scope": ["<final narrowed scope>"]
  }
}
```

### 2.1 Required Fields

| Field | Description |
|-------|-------------|
| `cert_version` | Certificate format version (currently "1.0") |
| `cert_id` | Globally unique certificate identifier |
| `created_at` | ISO 8601 timestamp of certificate assembly |
| `chain` | Ordered array of complete Trust Packets (root first, action last) |
| `chain_hashes` | Ordered array of Trust Packet Hashes (TPH) corresponding to each packet |
| `root_anchor` | The Authority Anchor that is the root of this chain |
| `terminal_action` | Summary of the final action for quick inspection |

### 2.2 Chain Ordering

- `chain[0]` MUST be signed by the Authority Anchor identified in `root_anchor`
- `chain[N]` (the last packet) MUST be the action being authorized
- Intermediate packets MUST be delegation packets (packet_type: "delegation")
- A chain of length 1 is valid — it represents direct authorization without delegation

---

## 3. Validation Rules

Verifiers MUST apply the following rules to an Authorization Certificate:

### 3.1 Chain Integrity

1. For each packet in the chain, compute the TPH and verify it matches the corresponding entry in `chain_hashes`
2. For each delegation packet `chain[i]` where `i > 0`, verify that the packet references `chain_hashes[i-1]` as its parent
3. Verify `chain[0]` is signed by the Authority Anchor's public key (discoverable via DNS)

### 3.2 Scope Monotonicity

For each adjacent pair `(chain[i], chain[i+1])`:
- The scope of `chain[i+1]` MUST be a subset of or equal to the scope of `chain[i]`
- Scope MUST NEVER expand across a delegation boundary

### 3.3 Temporal Validity

1. Every packet in the chain MUST NOT be expired at the time of verification
2. Each delegation's expiration MUST be less than or equal to its parent's expiration
3. If any packet in the chain is expired, the entire certificate is INVALID

### 3.4 Signature Verification

Each packet in the chain MUST pass independent Ed25519 signature verification:
- `chain[0]`: verified against the Authority Anchor's DNS-published public key
- `chain[i]` where `i > 0`: verified against the delegating entity's DNS-published public key

### 3.5 Fail-Closed

If any validation step fails, the entire Authorization Certificate MUST be rejected. There is no partial validity.

---

## 4. Certificate Assembly

An Authorization Certificate is assembled by the entity that holds the complete chain. Typically this is the final agent performing the action.

Assembly process:
1. Collect all Trust Packets in the delegation chain, from root to action
2. Compute the TPH for each packet
3. Verify hash links between adjacent packets
4. Package into the certificate structure
5. Generate a unique `cert_id`

The assembler does NOT add a signature to the certificate itself — the individual Trust Packet signatures are the proof. The certificate is merely a packaging format.

---

## 5. Transport

Authorization Certificates are transport-agnostic, like Trust Packets. They MAY be transmitted as:
- JSON body in an HTTPS POST
- Attachment or header in an email
- Embedded in a QR code (for short chains)
- Stored in a message queue
- Referenced by `cert_id` from an Authorization Ledger

Maximum recommended size: 64 KB (supports chains up to ~4 levels deep with typical packet sizes).

---

## 6. Relationship to Trust Packets

A Trust Packet is a single authorization. An Authorization Certificate is a chain of Trust Packets.

| Aspect | Trust Packet | Authorization Certificate |
|--------|-------------|--------------------------|
| Scope | Single action | Delegated chain of actions |
| Depth | 1 signature | N signatures (one per link) |
| Self-contained | Yes | Yes |
| Independently verifiable | Yes | Yes |
| Use case | Direct authorization | Delegated authorization |

An Authorization Certificate with a chain of length 1 is semantically equivalent to a standalone Trust Packet.

## 7. Example: AI Agent Purchase

```
Authority Anchor: user-device.example.com

chain[0] — Root Authorization (signed by user's device):
  subject: "psp@paymentservice.com"
  scope: ["charge:100"]
  packet_type: "delegation"
  → "I authorize this PSP to charge up to $100"

chain[1] — PSP Delegation (signed by PSP):
  subject: "claude@agent.example.com"
  scope: ["charge:50"]
  parent_tph: <hash of chain[0]>
  packet_type: "delegation"
  → "I delegate to this AI agent to charge up to $50"

chain[2] — Agent Action (signed by AI agent):
  subject: "claude@agent.example.com"
  action: "charge"
  scope: ["charge:49.99"]
  parent_tph: <hash of chain[1]>
  params: { item: "Nike Air Max", amount: 49.99 }
  → "Charge $49.99 for Nike Air Max"
```

Verifier checks: $49.99 ≤ $50 ≤ $100. All signatures valid. All hash links intact. All packets unexpired. **Certificate valid.**

---

## 8. Security Considerations

- **Chain manipulation:** Hash linking prevents insertion, removal, or reordering of packets
- **Scope escalation:** Monotonicity check prevents a delegate from exceeding granted authority
- **Expired root:** Temporal validation ensures a revoked Authority Anchor invalidates all downstream certificates
- **Stale certificates:** Certificates SHOULD be assembled fresh for each action, not cached

---

## 9. Conformance

An implementation is conformant with RFC 1400 if it:

1. Correctly assembles Authorization Certificates from ordered Trust Packet chains
2. Validates hash links between all adjacent packets
3. Enforces scope monotonicity across all delegation boundaries
4. Rejects the entire certificate if any single packet fails validation
5. Verifies each signature independently via DNS-published public keys
