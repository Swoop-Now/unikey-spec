## Abstract

The Authorization Ledger is a distributed, append-only, cryptographically verifiable record system in which each party to a transaction independently maintains an identical complete copy of the transaction's Authorization Certificate, where each copy is independently verifiable by any party using only the public keys embedded within the Certificate, without contact with any central authority, shared infrastructure, or consensus mechanism, and which may be operated by infrastructure-layer entities on behalf of entire participant ecosystems. The ledger serves three critical functions: replay prevention (rejecting previously-seen packet IDs), dispute resolution (proving what was authorized, by whom, and when), and compliance (satisfying the reproducibility requirements of RFC 4001). This specification defines the ledger entry format, chaining rules, query interface, distributed architecture, and operational requirements.

---

## 1. Introduction

Trust Packets prove that an action *is* authorized at the moment of verification. But they do not prove that an action *was* authorized at a point in the past. For payment networks, compliance, and dispute resolution, a durable record of authorized actions is essential.

The Authorization Ledger fills this gap. Unlike existing distributed record systems that require either centralized authority (traditional databases) or consensus mechanisms (blockchains), the Authorization Ledger achieves consistency through the mathematical properties of the Authorization Certificate hash chain. Each party independently maintains their own copy. No party's ledger depends on any other party's ledger. No consensus mechanism coordinates the copies. Consistency is guaranteed by the fact that each party received the same cryptographically chained record — any discrepancy between copies is detectable by comparing hash chains and signatures.

A distinguishing feature is suitability for **infrastructure-layer operation**: a telecom carrier, PSP, or payment network can operate an Authorization Ledger on behalf of an entire participant ecosystem, maintaining transaction records for every merchant or enterprise on their network without those participants operating their own ledger infrastructure.

## 2. Ledger Entry Format

Each entry in the Authorization Ledger is a JSON object:

```json
{
  "entry_id": 4821,
  "entry_hash": "<SHA-256 hash of this entry's canonical form>",
  "prev_hash": "<SHA-256 hash of entry 4820>",
  "recorded_at": "2026-03-24T10:30:00.123Z",
  "event_type": "verification_pass",
  "packet_id": "pkt_9844855e965bed3f",
  "packet_hash": "<TPH — SHA-256 of canonical Trust Packet>",
  "cert_id": "cert_abc123",
  "verification": {
    "result": "valid",
    "subject": "claude@agent.example.com",
    "issuer": "user-device.example.com",
    "audience": "payments@nike.example.com",
    "action": "charge",
    "scope": ["charge:49.99"],
    "signer": "user-device.example.com",
    "algorithm": "ed25519",
    "key_selector": "unikey",
    "verified_at": "2026-03-24T10:30:00.100Z"
  },
  "metadata": {
    "verifier": "stripe.example.com",
    "dns_resolvers_used": ["8.8.8.8", "1.1.1.1", "9.9.9.9"],
    "dns_consensus": true,
    "chain_depth": 2,
    "processing_time_ms": 4
  }
}
```

### 2.1 Required Fields

| Field | Description |
|-------|-------------|
| `entry_id` | Monotonically increasing sequence number |
| `entry_hash` | SHA-256 hash of this entry (excluding `entry_hash` itself) |
| `prev_hash` | SHA-256 hash of the previous entry (genesis entry uses a well-known seed) |
| `recorded_at` | ISO 8601 timestamp with millisecond precision |
| `event_type` | `verification_pass`, `verification_fail`, or `replay_rejected` |
| `packet_id` | The Trust Packet's unique identifier |
| `packet_hash` | The Trust Packet Hash (TPH) as defined in RFC 2001 |
| `verification` | The verification result (see §2.2) |

### 2.2 Verification Object

| Field | Description |
|-------|-------------|
| `result` | `valid` or `invalid` |
| `subject` | Who is asserting the action |
| `issuer` | The Authority Anchor domain |
| `audience` | The intended verifier |
| `action` | The authorized action |
| `scope` | The scope array from the Trust Packet |
| `signer` | The domain that signed the packet |
| `algorithm` | Cryptographic algorithm used |
| `verified_at` | When verification completed |

### 2.3 Optional Fields

| Field | Description |
|-------|-------------|
| `cert_id` | Authorization Certificate ID if delegation was involved |
| `metadata` | Implementation-specific operational data |
| `error` | Error details for failed verifications |

## 3. Chaining Rules

The ledger MUST maintain a hash chain for tamper evidence:

1. **Entry hash computation:** Canonicalize the entry (excluding `entry_hash`), compute SHA-256
2. **Chain linking:** `entry[N].prev_hash` MUST equal `entry[N-1].entry_hash`
3. **Genesis entry:** The first entry uses `prev_hash` = SHA-256 of the string `"unikey-ledger-genesis-v1"`
4. **Gap detection:** If `entry_id` values are not contiguous, the ledger has been tampered with

### 3.1 Immutability

Entries MUST NOT be modified or deleted after creation. The hash chain ensures that any modification to a historical entry invalidates all subsequent entries.

### 3.2 Ordering

Entries MUST be ordered by `entry_id`. The `recorded_at` timestamp MUST be monotonically non-decreasing.

---

## 4. Replay Prevention

The Authorization Ledger serves as the canonical replay prevention mechanism:

1. Before processing a Trust Packet, the verifier MUST check whether `packet_id` already exists in the ledger
2. If found, the verifier MUST reject the packet with error code TP-001 (Replay)
3. The rejection MUST be recorded as an `event_type: "replay_rejected"` entry

This replaces ad-hoc nonce stores with a durable, auditable mechanism.

---

## 5. Query Interface

Ledger implementations MUST support the following queries:

| Query | Parameters | Returns |
|-------|-----------|---------|
| Get by entry ID | `entry_id` | Single entry |
| Get by packet ID | `packet_id` | Single entry (or replay_rejected) |
| List by subject | `subject`, `from`, `to` | Filtered entries |
| List by signer | `signer`, `from`, `to` | Filtered entries |
| List by action | `action`, `from`, `to` | Filtered entries |
| List by time range | `from`, `to` | Entries in range |
| Verify chain | `from_entry_id`, `to_entry_id` | Chain validity |
| Get latest | — | Most recent entry with `entry_id` and `entry_hash` |

## 6. Verification Chain Audit

Any party with read access to the ledger can verify its integrity:

```
function auditLedger(entries):
  for i from 1 to len(entries) - 1:
    expected_prev = computeHash(entries[i-1])
    if entries[i].prev_hash != expected_prev:
      return TAMPERED at entry i
    if entries[i].entry_id != entries[i-1].entry_id + 1:
      return GAP at entry i
  return INTACT
```

## 7. Operational Requirements

### 7.1 Durability

Ledger entries MUST survive process restarts. Implementations SHOULD use durable storage (database, filesystem, or distributed log).

### 7.2 Availability

The ledger MUST be available for write during verification (to record results and check replays). Verification MUST fail closed if the ledger is unavailable.

### 7.3 Retention

Entries MUST be retained for a minimum of 7 years for payment-related actions, consistent with financial record-keeping requirements. Implementations MAY define shorter retention for non-payment actions.

### 7.4 Access Control

- **Write:** Only the verifier that produced the entry may write to the ledger
- **Read:** Read access policies are implementation-defined. Ledger entries for a specific subject SHOULD be available to that subject for dispute resolution.

---

## 8. Relationship to RFC 4001

RFC 4001 §6 requires:
- Decision logging with specific error codes
- Reproducibility — a third-party auditor can reproduce a verification decision

The Authorization Ledger satisfies both requirements. Each entry contains the verification result, the Trust Packet Hash (enabling re-verification), and the error code (for failed verifications). The hash chain ensures entries have not been altered.

## 9. Distributed Architecture

### 9.1 Independent Operation Without Shared Infrastructure

When a transaction completes and an Authorization Certificate is formed, each party to the transaction receives a complete, identical copy and appends it to their own independently-operated Authorization Ledger. No party's ledger depends on any other party's ledger. No consensus mechanism coordinates the copies. Consistency is guaranteed by the mathematical properties of the Authorization Certificate — each party received the same cryptographically chained record, and any discrepancy between copies is detectable by comparing hash chains and signatures.

### 9.2 Infrastructure-Layer Operation

A distinguishing feature of the Authorization Ledger is suitability for operation by infrastructure-layer entities on behalf of entire participant ecosystems:

- A **telecom carrier** operates a UniKey verification endpoint; every Trust Packet verified is logged to the carrier's Authorization Ledger; every merchant or enterprise on the carrier's network has their transaction records maintained without operating their own ledger infrastructure
- A **payment network** logs every authorized payment transaction for every merchant on their network through a single Authorization Ledger deployment
- A **PSP** logs every authorized payment for every merchant they serve

Each participant retains access to their records within the infrastructure operator's ledger. The operator's ledger serves as the authoritative record for the ecosystem.

### 9.3 Independent Verification

A party holding a ledger entry verifies its authenticity using only the public keys embedded within the Authorization Certificate: reconstruct the hash chain from embedded Trust Packet data; verify each signature against the corresponding embedded public key; confirm hash relationships are mathematically valid. No DNS lookup required at verification time. No UniKey infrastructure contact required. No contact with any other party's systems required.

### 9.4 Storage Technology Independence

This specification does not mandate a specific storage technology. The Authorization Ledger MAY be implemented as:

- A local database table with hash chain columns
- A distributed append-only log (e.g., Kafka with chain validation)
- A simple file with one JSON entry per line (for development/testing)

The hash chain provides tamper evidence regardless of the underlying storage technology. Consensus mechanisms (as used in blockchain) are explicitly NOT required — consistency is achieved through the mathematical properties of the Authorization Certificate.

## 10. Example: Dispute Resolution

1. User claims they did not authorize a $49.99 charge at Nike
2. Nike requests the ledger entry for the packet_id from Stripe
3. Stripe produces ledger entry #4821:
   - `packet_hash`: SHA-256 of the canonical Trust Packet
   - `verification.issuer`: `user-device.example.com` (the user's device)
   - `verification.action`: `charge`
   - `verification.scope`: `["charge:49.99"]`
   - `prev_hash` and `entry_hash`: proving the entry has not been tampered with
4. The user's device Authority Anchor (DNS public key) can re-verify the Trust Packet Hash
5. The hash chain proves the entry existed at the recorded time
6. **Dispute resolved:** The user's device authorized the charge

## 11. Prior Art Differentiation

**Blockchain:** Achieves distributed consensus through global ledger replication and consensus mechanisms. The Authorization Ledger is distinguished in that: (a) consistency is achieved through hash chain mathematics rather than consensus; (b) each party operates an independent copy rather than a shared ledger; (c) no consensus mechanism, mining, or staking is required; (d) verification requires no network participant contact; (e) infrastructure-layer operation on behalf of ecosystem participants has no blockchain equivalent.

**Certificate Transparency:** Append-only logs of certificate issuances verifiable by monitors. Distinguished in that: (a) records multi-party transaction authorization sequences rather than certificate issuances; (b) verification uses embedded keys rather than separate log infrastructure; (c) independently operated by each transaction party rather than designated log operators.

**Traditional Audit Databases:** Centralized, mutable, require central system contact for verification. Distinguished in that the Authorization Ledger is distributed, append-only by protocol specification (not access controls), and independently verifiable without central infrastructure.

## 12. Security Considerations

- **Tamper evidence:** Hash chain ensures any modification is detectable
- **Non-repudiation:** The combination of Ed25519 signatures (in the Trust Packet) and the ledger entry provides non-repudiation of authorization
- **Replay prevention:** Dual protection — Trust Packet expiration (temporal) plus ledger uniqueness check (permanent)
- **Privacy:** Ledger entries contain verification metadata, not payment card numbers or personal data. The Trust Packet itself may be stored separately or referenced by hash only.

---

## 12. Conformance

An implementation is conformant with RFC 2002 if it:

1. Records every verification decision (pass, fail, and replay) as a ledger entry
2. Maintains a hash chain with contiguous entry IDs
3. Supports replay detection via packet_id lookup
4. Provides the query interface defined in §5
5. Enforces append-only semantics at the protocol level — entries MUST NOT be modified or deleted
6. Fails verification closed if the ledger is unavailable for write
7. Supports independent verification of entries using only embedded public keys from the Authorization Certificate (no DNS lookup required)
8. Supports distributed operation where each transaction party independently maintains their own copy
