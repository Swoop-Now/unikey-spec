## Abstract

The Authorization Ledger is a distributed, append-only, cryptographically verifiable record system in which each party to a transaction independently maintains an identical complete copy of the transaction's Authorization Certificate, where each copy is independently verifiable by any party using only the public keys embedded within the Certificate, without contact with any central authority, shared infrastructure, or consensus mechanism. The ledger may be operated by infrastructure-layer entities (telecoms, PSPs, payment networks) on behalf of entire participant ecosystems. This specification defines the distributed architecture, ledger entry format, chaining rules, verification model, query interface, and operational requirements.

---

## 1. Introduction

Trust Packets prove that an action *is* authorized at the moment of verification. But they do not prove that an action *was* authorized at a point in the past. For payment networks, compliance, and dispute resolution, a durable record of authorized actions is essential.

The Authorization Ledger fills this gap. It is the distributed "receipt book" of the UniKey protocol — a chronological, tamper-evident log that records every verification decision. Each party to a transaction independently maintains their own identical copy. Consistency is guaranteed by the mathematical properties of the Authorization Certificate, not by synchronization or consensus.

---

## 2. Distributed Architecture

### 2.1 Independent Operation Without Shared Infrastructure

When a transaction completes and an Authorization Certificate is formed, each party to the transaction receives a complete, identical copy and appends it to their own independently-operated Authorization Ledger. No party's ledger depends on any other party's ledger. No consensus mechanism coordinates the copies.

Consistency is guaranteed by the mathematical properties of the Authorization Certificate — each party received the same cryptographically chained record, and any discrepancy between copies is detectable by comparing hash chains and signatures.

### 2.2 Infrastructure-Layer Operation

A distinguishing feature of the Authorization Ledger is its suitability for operation by infrastructure-layer entities on behalf of entire participant ecosystems:

- **Telecom carriers** may operate a UniKey verification endpoint where every Trust Packet verified is logged to the carrier's Authorization Ledger. Every merchant or enterprise on the carrier's network has their transaction records maintained without operating their own ledger infrastructure.
- **Payment networks** may log every authorized payment transaction for every merchant on their network through a single Authorization Ledger deployment.
- **PSPs** may log every authorized payment for every merchant they serve.

Each participant retains access to their records within the infrastructure operator's ledger. The operator's ledger serves as the authoritative record for the ecosystem. Participants MAY also maintain their own independent copies.

### 2.3 Consistency Without Consensus

Unlike blockchain systems that require consensus among network participants, the Authorization Ledger achieves consistency through the Authorization Certificate itself. Because the certificate is a cryptographically chained record with embedded public keys:

- Each party can independently verify that their copy is authentic and untampered
- Any discrepancy between parties' copies is detectable through hash chain comparison
- No consensus mechanism, mining, staking, or network participant contact is required
- Verification is a local mathematical operation, not a distributed coordination problem

## 3. Ledger Entry Format

Each entry in the Authorization Ledger is a JSON object:

```json
{
  "entry_id": 4821,
  "entry_hash": "<SHA-256 hash of this entry's canonical form>",
  "prev_hash": "<SHA-256 hash of entry 4820>",
  "recorded_at": "2026-03-24T10:30:00.123Z",
  "event_type": "verification_pass",
  "packet_id": "pkt_9844855e965bed3f",
  "packet_hash": "<TPH — SHA-256 of canonical Trust Packet>",
  "cert_id": "cert_abc123",
  "cert_hash": "<SHA-256 of the complete Authorization Certificate>",
  "verification": {
    "result": "valid",
    "subject": "claude@agent.example.com",
    "issuer": "user-device.example.com",
    "audience": "payments@nike.example.com",
    "action": "charge",
    "scope": ["charge:49.99"],
    "signer": "user-device.example.com",
    "algorithm": "ed25519",
    "key_selector": "unikey",
    "verified_at": "2026-03-24T10:30:00.100Z",
    "verification_method": "embedded_keys"
  },
  "metadata": {
    "verifier": "stripe.example.com",
    "chain_depth": 2,
    "signing_anchors": [
      "user-device.example.com",
      "paymentservice.com",
      "agent.example.com"
    ],
    "processing_time_ms": 4
  }
}
```

### 3.1 Required Fields

| Field | Description |
|-------|-------------|
| `entry_id` | Monotonically increasing sequence number |
| `entry_hash` | SHA-256 hash of this entry (excluding `entry_hash` itself) |
| `prev_hash` | SHA-256 hash of the previous entry (genesis entry uses a well-known seed) |
| `recorded_at` | ISO 8601 timestamp with millisecond precision |
| `event_type` | `verification_pass`, `verification_fail`, or `replay_rejected` |
| `packet_id` | The Trust Packet's unique identifier |
| `packet_hash` | The Trust Packet Hash (TPH) as defined in RFC 2001 |
| `verification` | The verification result (see S3.2) |

### 3.2 Verification Object

| Field | Description |
|-------|-------------|
| `result` | `valid` or `invalid` |
| `subject` | Who is asserting the action |
| `issuer` | The Authority Anchor domain |
| `audience` | The intended verifier |
| `action` | The authorized action |
| `scope` | The scope array from the Trust Packet |
| `signer` | The domain that signed the packet |
| `algorithm` | Cryptographic algorithm used |
| `verified_at` | When verification completed |
| `verification_method` | `embedded_keys` (from certificate) or `dns_lookup` (real-time resolution) |

### 3.3 Optional Fields

| Field | Description |
|-------|-------------|
| `cert_id` | Authorization Certificate ID (SHOULD be present for multi-party transactions) |
| `cert_hash` | SHA-256 hash of the complete Authorization Certificate |
| `metadata` | Implementation-specific operational data |
| `error` | Error details for failed verifications |

## 4. Chaining Rules

The ledger MUST maintain a hash chain for tamper evidence:

1. **Entry hash computation:** Canonicalize the entry (excluding `entry_hash`), compute SHA-256
2. **Chain linking:** `entry[N].prev_hash` MUST equal `entry[N-1].entry_hash`
3. **Genesis entry:** The first entry uses `prev_hash` = SHA-256 of the string `"unikey-ledger-genesis-v1"`
4. **Gap detection:** If `entry_id` values are not contiguous, the ledger has been tampered with

### 4.1 Append-Only by Protocol Specification

Entries MUST NOT be modified or deleted after creation. This append-only property is enforced at the **protocol specification level**, not dependent on access controls or administrative policy. Combined with the tamper-evident Authorization Certificate structure, the ledger provides a permanent, mathematically unalterable record of every completed authorized transaction.

The hash chain ensures that any modification to a historical entry invalidates all subsequent entries, making tampering detectable by any party holding a copy.

### 4.2 Ordering

Entries MUST be ordered by `entry_id`. The `recorded_at` timestamp MUST be monotonically non-decreasing.

## 5. Independent Verification

### 5.1 Verification Using Embedded Keys

A party holding a ledger entry verifies its authenticity using only the public keys embedded within the Authorization Certificate:

1. Reconstruct the hash chain from embedded Trust Packet data
2. Verify each signature against the corresponding embedded public key
3. Confirm hash relationships are mathematically valid
4. Confirm scope monotonicity across the chain

No DNS lookup is required at verification time. No UniKey infrastructure contact is required. No contact with any other party's systems is required. Verification is a purely local mathematical operation.

### 5.2 Ledger Chain Audit

Any party with read access to the ledger can verify its structural integrity:

```
function auditLedger(entries):
  for i from 1 to len(entries) - 1:
    expected_prev = computeHash(entries[i-1])
    if entries[i].prev_hash != expected_prev:
      return TAMPERED at entry i
    if entries[i].entry_id != entries[i-1].entry_id + 1:
      return GAP at entry i
  return INTACT
```

### 5.3 Cross-Party Verification

Because each party independently maintains an identical copy of the Authorization Certificate, discrepancies between parties' ledger copies are detectable through hash chain comparison without trusted third-party arbitration.

---

## 6. Replay Prevention

The Authorization Ledger serves as the canonical replay prevention mechanism:

1. Before processing a Trust Packet, the verifier MUST check whether `packet_id` already exists in the ledger
2. If found, the verifier MUST reject the packet with error code TP-001 (Replay)
3. The rejection MUST be recorded as an `event_type: "replay_rejected"` entry

This replaces ad-hoc nonce stores with a durable, auditable mechanism.

## 7. Query Interface

Ledger implementations MUST support the following queries:

| Query | Parameters | Returns |
|-------|-----------|---------|
| Get by entry ID | `entry_id` | Single entry |
| Get by packet ID | `packet_id` | Single entry (or replay_rejected) |
| Get by cert ID | `cert_id` | All entries for a certificate |
| List by subject | `subject`, `from`, `to` | Filtered entries |
| List by signer | `signer`, `from`, `to` | Filtered entries |
| List by action | `action`, `from`, `to` | Filtered entries |
| List by time range | `from`, `to` | Entries in range |
| Verify chain | `from_entry_id`, `to_entry_id` | Chain validity |
| Get latest | -- | Most recent entry with `entry_id` and `entry_hash` |

## 8. Operational Requirements

### 8.1 Durability

Ledger entries MUST survive process restarts. Implementations SHOULD use durable storage (database, filesystem, or distributed log).

### 8.2 Availability

The ledger MUST be available for write during verification (to record results and check replays). Verification MUST fail closed if the ledger is unavailable.

### 8.3 Retention

Entries MUST be retained for a minimum of 7 years for payment-related actions, consistent with financial record-keeping requirements. Implementations MAY define shorter retention for non-payment actions.

### 8.4 Distribution

When a transaction completes and an Authorization Certificate is formed, the certificate SHOULD be distributed to all transaction parties. Each party appends the certificate to their own ledger. The protocol does not mandate a specific distribution mechanism — certificates may be pushed, pulled, or distributed through infrastructure-layer operators.

### 8.5 Storage Technology Independence

This specification does not mandate a specific storage technology. The Authorization Ledger MAY be implemented as:

- A local database table with hash chain columns
- A distributed append-only log (e.g., Kafka with chain validation)
- A simple file with one JSON entry per line (for development/testing)

The hash chain provides tamper evidence regardless of the underlying storage technology. Consensus mechanisms (as used in blockchain) are explicitly NOT required — consistency is achieved through the mathematical properties of the Authorization Certificate.

---

## 9. Privacy Accommodations

Default entries contain complete transaction details identical across all parties. Where privacy or regulation requires selective disclosure:

- Ledger entries MAY share only metadata (identifiers, timestamps, verification status) while withholding content from specific Trust Packets
- The hash chain integrity of both the ledger and the embedded Authorization Certificate is preserved even with selective disclosure
- The unique Authorization Certificate identifier (`cert_id`) enables cross-system reference and retrieval in contexts where full disclosure is permitted
- Selective disclosure MUST NOT compromise the ability to independently verify the ledger entry using embedded keys

---

## 10. Relationship to RFC 4001

RFC 4001 S6 requires:
- Decision logging with specific error codes
- Reproducibility — a third-party auditor can reproduce a verification decision

The Authorization Ledger satisfies both requirements. Each entry contains the verification result, the Trust Packet Hash (enabling re-verification), and the error code (for failed verifications). The hash chain ensures entries have not been altered. The embedded public keys in the Authorization Certificate enable any third-party auditor to reproduce verification decisions without contacting any external system.

---

## 11. Prior Art Differentiation

### 11.1 Blockchain

Blockchain achieves distributed consensus through global ledger replication and consensus mechanisms. The Authorization Ledger is distinguished in that: (a) consistency is achieved through hash chain mathematics rather than consensus; (b) each party operates an independent copy rather than a shared ledger; (c) no consensus mechanism, mining, or staking is required; (d) verification requires no network participant contact; (e) infrastructure-layer operation on behalf of ecosystem participants has no blockchain equivalent.

### 11.2 Certificate Transparency

Certificate Transparency maintains append-only logs of certificate issuances verifiable by monitors. The Authorization Ledger is distinguished in that: (a) it records multi-party transaction authorization sequences rather than certificate issuances; (b) verification uses embedded keys rather than separate log infrastructure; (c) it is independently operated by each transaction party rather than designated log operators.

### 11.3 Traditional Audit Databases

Traditional audit databases are centralized, mutable, and require central system contact for verification. The Authorization Ledger is distinguished in that it is distributed, append-only by protocol specification (not access controls), and independently verifiable without central infrastructure.

## 12. Example: Dispute Resolution

1. User claims they did not authorize a $49.99 charge at Nike
2. Nike requests the ledger entry for the `cert_id` from Stripe
3. Stripe produces ledger entry #4821 containing the Authorization Certificate:
   - `cert_id`: `cert_abc123` — the unique transaction record
   - The complete multi-party chain: user device -> PSP -> AI agent
   - All three parties' embedded public keys
   - Cumulative hash chain proving no tampering
   - `verification.issuer`: `user-device.example.com` (the user's device)
   - `verification.action`: `charge`
   - `verification.scope`: `["charge:49.99"]`
4. Any third party can independently verify the Authorization Certificate using only the embedded public keys — no DNS lookup, no contact with Stripe or the user's device
5. The ledger hash chain proves the entry existed at the recorded time and has not been altered
6. The user's own ledger copy contains an identical Authorization Certificate, independently verifiable
7. **Dispute resolved:** The user's device authorized the charge, provable by any party using only the embedded cryptographic evidence

## 13. Security Considerations

- **Tamper evidence:** Hash chain ensures any modification to a ledger entry is detectable; any modification to an Authorization Certificate is detectable through cumulative hash chain verification
- **Non-repudiation:** The combination of Ed25519 signatures from multiple Authority Anchors (embedded in the Authorization Certificate) and the ledger entry provides non-repudiation of authorization
- **Replay prevention:** Dual protection — Trust Packet expiration (temporal) plus ledger uniqueness check (permanent)
- **Independent verification:** Embedded public keys enable any party to verify any ledger entry without external infrastructure — verification is a local mathematical operation
- **Distributed resilience:** Because each party independently maintains their own copy, no single point of failure can destroy the transaction record
- **Privacy:** Ledger entries contain verification metadata, not payment card numbers or personal data. Selective disclosure accommodations allow partial sharing while preserving hash chain integrity. The Trust Packet itself may be stored separately or referenced by hash only.

---

## 14. Conformance

An implementation is conformant with RFC 2002 if it:

1. Records every verification decision (pass, fail, and replay) as a ledger entry
2. Maintains a hash chain with contiguous entry IDs
3. Supports replay detection via packet_id lookup
4. Provides the query interface defined in S7
5. Enforces append-only semantics at the protocol level — entries MUST NOT be modified or deleted, independent of access controls
6. Fails verification closed if the ledger is unavailable for write
7. Supports independent verification of ledger entries using only the public keys embedded within the Authorization Certificate
8. Supports distributed operation where each transaction party independently maintains their own ledger copy
